# Security model

mini-harness binds to `127.0.0.1` and requires a bearer credential on its API. The instance credential survives a restart. On Unix it is stored in an owner-only file. Windows protects the credential using DPAPI for the current user. The server metadata and detached log omit the credential. Run `mini-harness reset-token` to stop the instance and revoke its current credential.

## Workspace and execution

- The native file tools and workspace browser use the same File Access provider. They restrict access to the active workspace and exclude mini-harness storage. Explicit file operations reject links, junctions, nonregular files and files with multiple hard links. Linux opens directories relative to pinned descriptors and verifies the resolved location and file identity before using it. Keep workspace directories under your control when other local actors can rename or remount them.
- Windows and other non-Linux platforms check resolved paths, link types and file identity before I/O. These checks assume the workspace is protected from concurrent path changes by untrusted local processes. They provide workspace-level restrictions in a trusted local environment. OS-level containment against concurrent local filesystem manipulation requires a platform-specific sandbox.
- Shell starts disabled. In Standard conversations, each enabled built-in Shell operation waits for explicit Web approval, expiring after five minutes; cancellation rejects pending approval. Full access is an explicit per-conversation choice that bypasses Shell approval, including pending requests, but does not enable disabled plugins, override inherited read-only mode or change sandbox isolation. Linux isolated mode requires bubblewrap at `/usr/bin/bwrap`, working namespaces and `prlimit`. Isolated requests fail on hosts without these capabilities. It uses a separate PID and network namespace, clears the environment, exposes the workspace read-write, the current conversation's uploads and a limited set of system paths read-only, and applies per-process CPU, file size and descriptor limits. Separate the workspace from the configuration directory. On Linux, timeout, cancellation and output limits terminate the process group. Per-process limits do not constitute a system-wide resource quota.
- Trusted host mode runs with your user permissions. On Windows, command-tree termination uses `taskkill` while the parent process exists. Local Cordis JavaScript plugins run in-process with your user permissions on every platform. Replacing any default service through explicit Profile composition (including tool registration or authorization) trusts the replacement to preserve the required behavior. File Access, Process Execution and Sandbox providers are trusted code. Enable only reviewed plugins. Browser extensions run with access to the authenticated API. Installing a Profile dependency does not activate it; declare and enable the corresponding entry explicitly.
- Read-only conversations select registrations that declare read-only access, whether shipped or third-party. Descendants inherit read-only mode. This is a convention for normal agent tool execution, not an isolation boundary for trusted in-process JavaScript plugins. Process isolation for JavaScript plugins depends on the environment running the harness.
- The Skills plugin reads bounded instruction files and follows symbolic links and Windows junctions, including links outside configured roots. The file target must be regular and have one hard link. Workspaces and linked skill files may be controlled by an untrusted repository or another local user. Review their instructions and link targets before loading them. Skills discovery runs with the harness process's filesystem access. File Access and Shell use their own containment policies.

## Data

Native JSONL session logs live under `~/.mini-harness/sessions`. Deleting an indexed conversation recursively removes its descendants and their owned files. Backups, filesystem snapshots and provider-side logs are controlled outside mini-harness.

Provider credentials can come from the environment or `~/.mini-harness/auth.json`. Original uploads are stored within the owning conversation's managed directory. Supported images and bounded UTF-8 text are sent to the selected provider; other files are available to enabled Shell commands and are not automatically parsed. Model requests send conversation content and selected tool results to the chosen provider.

Session messages and inbox acknowledgments are flushed before completion is reported. Checksums, sequence numbers and ancestry detect corrupt complete records; only an incomplete final write is discarded at recovery. Restart marks unfinished runs interrupted and never retries tools automatically. A tool interrupted before its result was committed has an unknown outcome; the next turn receives an explicit error result rather than silently rerunning it.

The conversation catalog is validated at startup: invalid identities, unknown workspaces and broken ancestry are rejected instead of loading a partial index.

A trusted gateway plugin may expose a separately authenticated viewer. The gateway owns viewer authentication, route authorization, pairing credentials and listener lifecycle. The Host forwards any authorized registered route without a business-route allowlist; it still checks the forwarded Origin/Host and restricts shutdown to local access. A gateway that intends read-only access must enforce that policy itself.

The Profile YAML parser accepts data-only configuration layers. Disabled entries are not imported; npm lifecycle scripts are disabled by default. Browser entries receive their configuration. Store credentials in the existing secrets service rather than in browser configuration. Preview routes use the selected scoped File Access provider or the owning conversation’s attachment store. Media uses temporary Blob URLs. Uploaded markup is displayed as source or passed through the app’s sanitized Markdown renderer.
